# Передача backend команде DT-20

На ветке C реализованы ручной и организаторский импорт, версии диалогов и чек-листов,
очередь заданий, апелляции и экспорт. SQLite хранит неизменяемый снимок диалога,
исходные ответы, исходный балл, решения и эффективный балл. На рабочем компьютере
используйте API на loopback и один процесс uvicorn. Пользователи этого компьютера,
имеющие доступ к API, могут читать данные и принимать решения. Для работы с реальными
данными вне него команде нужен защищённый доступ.

## Как B проверить интеграцию

1. Отправьте пример из [контракта API](API_CONTRACT.md) в `POST /api/v1/conversations/import`.
   Ответ содержит `imported_count=1` и ID версии. Повтор даёт `unchanged_count=1`
   и тот же ID. Измените текст и снова откройте первую версию по её ID.
2. Для проверки очереди возьмите ID диалога и чек-листа из `GET /api/v1/demo`.
   Передайте их в `POST /api/v1/evaluations` с `mode="mock"`. Ответ 202 содержит ID задания.
   Опросите `GET /api/v1/evaluations/{id}` до succeeded или failed.
   Mock доступен для встроенного примера. В этом примере исходный результат равен 85.38.
3. Отправьте `{"criterion_id":"C01","comment":"Проверка приветствия"}` в
   `POST /api/v1/evaluations/{id}/appeals`. Передайте возвращённый ID в
   `POST /api/v1/appeals/{id}/decision` с телом ниже. После решения запросите
   оценку: effective_score меняется, original_score и evidence сохраняются.

```json
{"action":"override","reason":"Учебная поправка","override_answer":{"type":"boolean","value":false},"idempotency_key":"demo-review-1"}
```

Сценарий проверен через HTTP с повтором после перезапуска. Более подробные варианты
ошибок описаны в OpenAPI и в `backend/tests/api/test_http_workflow.py`. Готовность
экрана редактора, проигрывания реальной записи и апелляций через UI принимают B и C вместе.

## Проверка безопасности

| Приоритет | Что воспроизведено | Исправление и проверка |
| --- | --- | --- |
| Высокий, 01 | Ручной импорт с именем разрешённой группы позволял поставить произвольный текст на живую оценку | Перед постановкой и каждой сетевой попыткой проверяются происхождение, членство версии в текущей группе и разрешённый план. Отрицательные случаи покрывают подмену группы и замену записи после постановки. `backend/app/services/live_workflow.py:47` |
| Высокий, 02 | При ошибке записи SQLAlchemy включал параметры SQL с подписанным аудиоадресом в текст исключения | Параметры скрыты на уровне engine. Тест принудительно вызывает ошибку записи и проверяет отсутствие маркера. `backend/app/storage/database.py:22` |
| Средний, 03 | Файлы журналов SQLite, отдельные типы ключей и подписанные облачные URL могли пройти проверку индекса Git | Guard проверяет staged-версию и выводит имя файла. Тест использует искусственные маркеры и временный Git-репозиторий. `scripts/check_public_files.py:10` |

Дополнительные тесты проверяют лимит загрузки, запрет записи с постороннего Origin,
валидацию Host, скрытие исходных данных из ошибок, фиксированный HTTPS-адрес источника,
лимиты аудио и отсутствие переходов по перенаправлениям. Браузер получает ссылку на
маршрут конкретной версии. Утверждённые источники аудио настраиваются через CQA_AUDIO_ORIGINS.
Проверки зависимостей по текущим базам npm и PyPI не нашли известных уязвимостей в проверенных версиях.
