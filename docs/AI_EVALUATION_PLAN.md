# План проверки качества AI

Владелец — A; ручные спорные эталоны проверяют минимум два участника.
Смысловой ориентир — исходная автоматическая оценка. Апелляции улучшают продуктовый
процесс, но не подменяют исходные ответы при отчёте точности.

## Baseline

Сначала один генеративный provider через общий async EvaluationProvider.
Модель выбирается после проверки доступности, прав обработки и бюджета.
Ранее рассматривавшийся Gemini Flash — кандидат, точный model ID ещё не утверждён.
В bootstrap live не запускается, бюджет пока 0.

Модель получает immutable snapshots диалога и всех активных критериев с определениями
каждой ступени и N/A. Не использовать только названия критериев и восемь hardcoded prompts.
conversation_id не служит содержательным признаком; его изменение не меняет решение.
Инструкции внутри транскрипта — недоверенный текст, не команды оценщику.

Pipeline: ответ → parsing/typed validation → полнота критериев/значений/N/A →
принадлежность evidence snapshot → scorer. Допустим ограниченный retry/repair с учётом
стоимости; исчерпание попыток даёт failed. Не подставлять 0/Нет/N/A при ошибках.
Объяснение краткое, проверяемое; скрытая цепочка рассуждений не нужна.

## Набор и разделение

При отсутствии официальных DEV-эталонов вручную разметить ориентировочно 20–25 диалогов.
Это **эталоны команды**, не Ground Truth организаторов.
Например, для 24 диалогов заранее выделить 15 на настройку и 9 на отложенную проверку.
Переводы и вариации одного сценария держать в одной части.
Не использовать holdout для непрерывной настройки; после итераций нужен новый
независимый контроль либо честное описание утраты независимости.

Покрыть RU/KZ/EN, оба канала, применимость и редкие нарушения.
KZ размечает человек, понимающий текст. Ответ другой LLM не становится эталоном
без человеческой проверки. По звонкам и неподтверждённым регламентам отмечать допущения.

## Метрики и отчёт

| Что измерять | Зачем |
| --- | --- |
| Exact match каждого критерия и confusion matrix | Найти систематическое неверное понимание |
| MAE итогового балла | Оценить величину отклонения |
| Отдельные ошибки N/A | Не скрывать провалы применимости общей точностью |
| Ступени C04/C06 | Выявить частичные, а не бинарные ошибки |
| Precision/recall C08 и примеры ошибок | Редкий flag не должен теряться в среднем |
| Техническая и смысловая корректность evidence | Валидная ссылка не всегда подтверждает вывод |
| Failure rate, latency, tokens, cost всех attempts | Проверить практическую пригодность |

MAE/accuracy — диагностические показатели команды; официальная формула жюри не объявлена.
Сравнивать одинаковые snapshots. В отчёте сохранять provider/model/instruction/pipeline,
checklist version, hashes диалогов, split, размеры групп, ошибки и ограничения.
Нельзя обещать процент точности по малой выборке или совпадению двух моделей.

Смысловые случаи: бот-приветствие, исходно достаточные данные, требуемая неподтверждённая
идентификация, общий вопрос без идентификации, правильный следующий шаг, неполный ясный ответ,
спокойный клиент, операторское закрытие без прощания, частная платная услуга,
задержка >3 минут без придуманного штрафа, смена ID, prompt injection в транскрипте.
Это eval cases, не нестабильные платные тесты обычного CI.

## Jev — только после baseline

Проверить текущий API TypeSafe перед интеграцией. Начальный эксперимент — Choice
с описаниями всех допустимых ответов. Score может представлять среднюю позицию,
его нельзя напрямую считать официальной ступенью C04/C06.
N/A не означает низкую confidence; confidence не является измеренной вероятностью
правильности на нашем наборе и не умножается на баллы.

Jev не даёт свободное объяснение: нужен проверяемый способ evidence/обоснования.
Если дополнительная LLM находит противоречие, решение пересматривается,
а не автоматически оправдывается. Совпадение двух моделей не доказывает истину.
Выбирать pipeline по отложенной проверке с учётом стоимости всех вызовов.

## Live и воспроизводимость

Live-eval — отдельная явная команда, которую A реализует с provider/model,
max cases/requests, timeout и разрешённым бюджетом. Не запускать live обычным pytest/CI.
Секреты вводятся в локальную среду; реальные transcripts/traces и полные eval results —
в private-каталогах. Для сдачи публикуются только две проверенные обезличенные
итоговые выжимки по [RESULTS_SUBMISSION](RESULTS_SUBMISSION.md), без исходных текстов.
Цены берутся из актуального официального источника с датой; неизвестная cost = null.
Контрольные 10 новых транскриптов проходят тот же код без готовых ответов и ручной подмены.
