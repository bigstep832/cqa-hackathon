# Сдача результатов CQA · формат 1.0

Это обязательный P0 в дополнение к работающему приложению. Основание — все три
страницы `CQA_Student_Guide_Appendix_Results.pdf`; инженерная организация работы —
`CQA_RESULTS_SUBMISSION_UPDATE_FOR_CODEX.txt`. Исходные вложения не публикуются.
PDF описывает формат, но не содержит отдельного файла JSON Schema.

Состояние: спецификация A готова; экспортёр, отдельный валидатор и команда сдачи
ещё **не реализованы** (C-06). A-01 сохраняется выполненной в согласованном
офлайн-объёме. Настоящие AI-прогоны и их качество не подтверждены.

## Обязательные требования организаторов

| Файл в публичном репозитории | Набор | Число записей |
| --- | --- | --- |
| `results/dev/results.json` | Все DEV: 60 чатов и 5 звонков | 65 |
| `results/prod/results.json` | Новые контрольные чаты | 10, включая ошибки |

Оба файла должны быть закоммичены **и отправлены push до стоп-кода**, доступны по
заранее переданной организаторам ссылке на репозиторий/сдаваемую ветку. Локальный
commit не является сдачей. Контроль появляется через 23 часа от старта; получение,
реальная оценка, проверка, commit, push и проверка доступности должны уложиться
до 24-го часа. Способ получения PROD объявляют организаторы; нельзя заранее
считать, что достаточно заменить `group_id` в DEV URL.

Точная дата/время, настоящее название команды и сдаваемая ветка пока не подтверждены.
Не создавать фиктивный PROD, не переименовывать DEV в PROD и не заполнять результаты
заглушками ради наличия файлов. Репетиция хранится отдельно в `work/`.

### Структура JSON

UTF-8, строгий JSON без комментариев и завершающих запятых. Корень — один объект:

| Поле | Значение |
| --- | --- |
| `schema_version` | Строка `"1.0"` |
| `team_name` | Настоящее название команды |
| `model.mode` | `local`, `external_api` или `hybrid` |
| `model.name` | Название фактически использованной модели; при нескольких — перечисление |
| `results` | Массив с одной записью на каждый исходный `conversation_id` |

DEV/PROD определяются каталогом. Исходные ID сохраняются без замены, изменения,
дублей и пропусков. Не экспортировать внутренний `ConversationVersion.id` вместо
`ConversationVersion.conversation_id`.

При успехе запись содержит `conversation_id`, `status: "ok"`, `criteria` и `score`.
В `criteria` ровно восемь объектов; каждый имеет `criterion_id`, `value`, краткое
`rationale` и `evidence_turns`. Каждый официальный критерий встречается ровно один раз.

| Внутренний ID | Официальный `criterion_id` | Допустимое `value` | Вес |
| --- | --- | --- | --- |
| C01 | `contact` | `true` / `false` | 10 |
| C02 | `discovery` | `true` / `false` / `null` | 15 |
| C03 | `identification` | `true` / `false` / `null` | 20 |
| C04 | `consultation` | 0 / 5 / 10 / 15 / 20 / `null` | 20 |
| C05 | `empathy` | `true` / `false` | 15 |
| C06 | `dialogue` | 0 / 4 / 7 / 10 | 15 |
| C07 | `closure` | `true` / `false` / `null` | 5 |
| C08 | `critical` | `true` / `false` | Не входит в итог |

Числа — исходные ступени **до применения веса**: C06 со ступенью 7 экспортируется
как `7`, не `10.5`. JSON boolean не является допустимой числовой ступенью.
`null` означает N/A и допустим только в четырёх строках таблицы.

`score` содержит `final_score` — JSON **число**, от 0 до 100, округлённое до двух
знаков, и `critical_flag` — boolean, равный значению `critical`. Внутренняя строковая
сериализация Decimal не подходит внешнему формату. N/A исключает вес; критическая
ошибка не обнуляет итог. `85.3` и `85.30` обозначают одно число.

`evidence_turns` — номера с **1 по всему исходному transcript**: учитываются
оператор, клиент, бот, system/события. Оцениваются действия оператора; контекстные
сообщения допустимы как доказательства. Не выдумывать номера или цитаты.

При ошибке сохранить исходный ID и записать `status: "error"`, `criteria: []`,
`score: null`, `error` с краткой действительной причиной. Ошибка не заменяется
нулём, N/A, ответом «Нет» или mock. Ошибочные записи входят в требуемое число.

## Решения команды для реализации

Это формализация требований и инструкции TXT, а не дополнительные цитаты PDF.
Формула и внутренняя динамическая рубрика остаются прежними.

1. **Отдельный выходной контракт.** [results.schema.json](../contracts/results.schema.json)
   — подготовленная A JSON Schema Draft-07. Она не меняет API DTO/OpenAPI/TS.
   Структурно допускаются пакеты на 10 или 65 записей; C отдельно проверяет число
   для выбранного DEV/PROD. Схема запрещает лишние поля, пустые пояснения и пустые/
   повторяющиеся evidence. Это консервативные решения команды; PDF не задаёт
   `additionalProperties`, сортировку, уникальность или минимальную длину evidence.
2. **Официальный snapshot.** Зафиксировать с A ID и content hash неизменяемого
   официального чек-листа на основе `config/checklists/default.v1.json`. Совпадение
   только C01–C08 недостаточно: проверить формулировки, веса, типы, шкалы и N/A.
   Оценку с изменённой рубрикой, включая дополнительные критерии, не экспортировать
   простым отбрасыванием полей; выполнить отдельную оценку по официальному snapshot.
   Основной продукт продолжает поддерживать произвольные критерии.
3. **Исходный AI, единый scorer.** Взять `Evaluation.output.answers`, проверить оба
   snapshot и `validate_output`, пересчитать существующим `domain.scoring.score`,
   сверить `original_score`. Апелляции и `effective_score` в сдачу не попадают.
   C08 берётся именно из исходного ответа C08. Округление — действующий
   `Decimal / ROUND_HALF_UP`; отдельной frontend/exporter-формулы нет. Несоответствие
   сохранённого итога — ошибка проверки, а не повод молча исправить историю.
4. **Исходные позиции.** Импорт C сохраняет порядок всех сообщений исходного массива.
   Преобразование: `message_id → order + 1` в оценённом snapshot. Диапазон раскрыть
   включительно, объединить пересечения, убрать повторы, отсортировать. Проверить
   привязку snapshot и пределы `1..len(messages)`. Не считать позиции в UI-фильтре.
5. **Полный независимый manifest.** Сохранить приватно полный исходный набор ID и
   snapshots при импорте, проверить уникальность самих исходных ID и равенство
   множеств с экспортом. Не строить manifest из готовых predictions: runner допускает
   `max_cases` и несколько версий одного диалога. Для каждого внешнего ID выбрать
   ровно один согласованный snapshot/evaluation, без выбора «лучшего балла».
   Если импорт нормализовал ID (например, удалил пробелы), выявить это и сохранить
   точное исходное значение или остановить импорт; не молча менять ID при экспорте.
6. **Ошибки и незавершённые задания.** `failed` превращается в `error` с очищенной
   причиной. Отсутствующее/незавершённое задание до повторной попытки блокирует
   готовность; при окончательном формировании пакета сохраняется как явная ошибка
   с причиной, а не пропуск или успех. Общая порча manifest/рубрики/конфигурации
   останавливает формирование файла, а не создаёт пачку фиктивных ответов.
7. **Происхождение.** Для официальных файлов отклонять mock, тестовый транспорт и
   репетиционные данные команды. `metadata.mode="live"` само по себе не доказывает
   сетевой прогон. Нужны исходный organizer manifest и сохранённые plan/attempts/
   metadata реального запуска, включая ошибки. Предоставленные организаторами
   synthetic DEV-чаты допустимы при настоящей AI-оценке; запрет касается наших fixtures
   и подставных результатов. Внутренние `mock/live` не равны внешним режимам модели.
8. **Модель.** По фактическим attempts: только локальная модель → `local`, только
   внешние API → `external_api`, сочетание обоих → `hybrid`. Несколько внешних API
   остаются `external_api`. Несколько имён перечислять однозначно в одной строке
   с провайдером и model ID, в стабильном порядке. Это трактовка команды; PDF не
   уточняет hybrid и разделитель. Если ни одного обращения к модели не состоялось,
   не выдумывать «фактически использованную» модель: требуется уточнение организаторов.
9. **Публичный файл — только итоговая выжимка.** Не включать транскрипты, аудио,
   подписанные URL, ключи, локальные пути, исходный ответ провайдера или traces.
   `rationale` объясняет поведение без персональных данных и дословных чувствительных
   цитат; `error` не содержит секретных деталей exception. A проверяет смысл и
   обезличенность, C — публикацию. ID сохраняются согласно формату организаторов.
   Одних regex и `check_public_files.py` недостаточно для проверки приватности.

Платные вызовы сейчас запрещены. Перед настоящим прогоном согласовать модель,
предельный бюджет и передачу данных внешнему провайдеру. Добавление требований
сдачи не снимает это ограничение.

## Что обязан проверить валидатор C-06

Валидатор работает офлайн и завершается ненулевым exit code при ошибке. JSON Schema
проверяет лишь структуру; следующие проверки требуют приватных входов/метаданных.

| Проверка | Положительный и отрицательный сценарии |
| --- | --- |
| JSON и схема | UTF-8; отклонить duplicate keys, NaN/Infinity, лишние поля, строки вместо чисел |
| Полнота | DEV ровно 65 (60 чатов + 5 звонков); PROD ровно 10 чатов; точный набор ID manifest, без дублей/подмен |
| Критерии | Все восемь ровно один раз; нет C09; raw scale; boolean не принимается за 0/1; N/A только где разрешено |
| Evidence | Все роли, позиции с 1; конец диапазона включён; отклонить чужой snapshot, неизвестный message ID и номер вне transcript |
| Баллы | Пересчёт тем же scorer; числовой итог с точностью до сотых; C08 согласован с flag; N/A не превращается в 0 |
| История | Экспорт original, не appeal/effective; изменённая официальная рубрика отклоняется |
| Ошибки | Сохранён ID; пустые criteria и null score; причина без секретов; неуспех не подменён mock |
| Происхождение | Реальный organizer manifest и запуск; fixtures/test transport не проходят в официальные пути |
| Публикация | Team/model реальные; rationale/error просмотрены; оба файла видны в сдаваемом публичном commit до срока |

Контрольный арифметический вектор из примера PDF: `true, null, null, 15, true, 7,
true, false` в порядке таблицы; числитель 55.5, знаменатель 65, итог **85.38**,
critical flag **false**. Другие граничные векторы: все применимые ответы максимальны
→ 100; все применимые минимальны → 0; смена только C08 сохраняет итог.
Для официальных восьми критериев знаменатель не может быть нулевым, поскольку
C01/C05/C06 не допускают N/A. `score: null` недопустим при `status: "ok"`.

Не считать структурную валидацию доказательством точности AI или успешной сдачи.
Проверка сотых должна использовать Decimal, чтобы не отвергать корректные суммы
из-за арифметики float в реализации JSON Schema.

## Передача C и контрольный час

- A-04: эта спецификация, схема и семантическое ревью реализации C. A-02 продолжает
  работу над качеством; A-01 не переделывается. B продолжает frontend.
- C-06, P0: экспортёр, отдельный валидатор, backend-тесты, одна команда
  «экспорт → проверка → отчёт», без раскрытия секретов. Фактический CLI C добавляет
  сюда после реализации; готовой команды в этой версии нет.
- До 23-го часа C проводит офлайн-репетицию на специально созданных synthetic
  входах вне официальных путей; проверяет отказы валидатора. После разрешённого
  AI-прогона готовит настоящий DEV, проверяет и публикует его заранее.
- 23–24: получить PROD → зафиксировать manifest → оценить тем же pipeline →
  экспортировать → проверить оба файла → просмотреть staged diff → commit → push →
  открыть оба пути в сдаваемом публичном commit → зафиксировать SHA. Оставить
  запас на повтор/ошибку провайдера и push; не начинать разработку экспортёра в этот час.
- `.gitignore` уже разрешает оба пути. Не добавлять туда реальные исходные данные.
  `scripts/freeze.py` сейчас только фиксирует метаданные: он не экспортирует,
  не валидирует формат и не отправляет результаты в GitHub.

После стоп-кода нельзя дополнять обязательный PROD, исправлять сдаваемые JSON или
продлевать срок ссылкой на возможность менять данные/чек-лист через UI на защите.
Подробная процедура сдачи — [DEMO](DEMO.md), проверки — [ACCEPTANCE](ACCEPTANCE.md).
