# Рубрика и расчёт

Каноническая конфигурация: [default.v1.json](../config/checklists/default.v1.json).
Канонические типы: [models.py](../backend/app/contracts/models.py).
Scorer: `app.domain.scoring.score(checklist, answers)`;
валидация: `validate_answers(checklist, answers)`.
Ни UI, ни модель не создают второй авторитетный итог.

## Исходная рубрика

Оцениваем оператора. Реплики client/bot/system остаются контекстом; приветствие бота
не засчитывается оператору. Системное событие может подтвердить идентификацию или закрытие.

| ID | Критерий | Ответы | Вес | N/A |
| --- | --- | --- | ---: | --- |
| C01 | Установление контакта | Да / Нет | 10 | Нет |
| C02 | Выявление потребности | Да / Нет / N/A | 15 | Данных для ответа хватало с самого начала |
| C03 | Идентификация | Да / Нет / N/A | 20 | Запрос не требовал идентификации |
| C04 | Корректная и полная консультация | 0, 5, 10, 15, 20 / N/A | 20 | Чат закончился до формулировки запроса |
| C05 | Эмпатия и клиентоориентированность | Да / Нет | 15 | Нет |
| C06 | Управление диалогом, скорость и грамотность | 0, 4, 7, 10 | 15 | Нет |
| C07 | Завершение | Да / Нет / N/A | 5 | Чат оборвался до возможности завершения |
| C08 | Грубые ошибки | Да / Нет | Без веса/баллов | Нет |

**C01:** Да только если оператор поздоровался на языке клиента и представился в первом ответе.

**C02:** Да, если учёл известные детали и уточнил недостающее до ответа.
Требовавшееся, но пропущенное уточнение — Нет, не N/A.

**C03:** Да требует подтверждённой проверки личности до раскрытия данных/защищённого
действия. Просьба пройти проверку не доказывает завершение. Если требуемая проверка
не подтверждена, ответ Нет; общий вопрос о тарифах может дать N/A.

**C04:**

| Ответ | Определение |
| ---: | --- |
| 20 | Все существенные вопросы закрыты или дан корректный следующий шаг |
| 15 | Основной вопрос решён, пропущена второстепенная деталь |
| 10 | Часть запроса закрыта, существенный вопрос остался открытым |
| 5 | Есть общая подсказка, но клиенту непонятно, как действовать |
| 0 | Ответа по существу нет или ключевая рекомендация ошибочна |

Отсутствие решения не означает N/A. При нехватке регламентов нельзя выдумывать
правильные тарифы или внутренние правила; ограничение отмечается в объяснении.

**C05:** Да означает вежливость и реакцию на конкретную проблему, когда клиент
описал неудобство или недовольство. В спокойном диалоге отдельное сочувствие не требуется.

**C06:**

| Ответ | Определение |
| ---: | --- |
| 10 | Ясные, связные ответы; при явном ожидании оператор предупредил |
| 7 | Один заметный сбой, но ответ понятен и диалог может продолжаться |
| 4 | Клиент переспрашивает из-за формулировок или порядка ответов |
| 0 | Бессвязность/противоречия делают ход диалога непонятным |

C04 оценивает полноту и правильность, C06 — понятность и последовательность.
Ясный ответ только на один из двух вопросов может иметь высокий C06 и частичный C04.

**C07:** Да = (подведён итог ИЛИ предложена дальнейшая помощь) И прощание.
Закрытие оператором без прощания после ответа — Нет. Это явная интерпретация
союзов исходной формулировки, согласованная с примером в официальной памятке.

**C08:** Да означает нарушение: оскорбление, предложение платной услуги в обход
компании или раскрытие конфиденциальной информации. Достаточно предложения
перевести деньги оператору лично для инвестирования либо дать личный номер
для платной частной консультации. Согласие клиента/перевод не нужны.
Обычная неточность, задержка или сам запрос телефона не создают флаг автоматически.

Порог первой реакции 3 минуты, теги и вложения исключены. Дополнительные штрафы,
обнуление за C08, дикция и интонация не входят в исходную оценку.

## Формула

Для применимых scored-критериев A: вес w, доля выполнения q.
Да → q=1; Нет → q=0; C04 → ответ/20; C06 → ответ/10.
Для новых шкал/категорий `options[].quality` явно задаёт q в [0,1].
У flag нет weight/quality; флаг определяется `options[].flagged`, а не номером C08.

```text
W = Σ w_i, i ∈ A
earned = Σ(w_i × q_i), i ∈ A
total = round_to_2(100 × earned / W)
```

N/A исключается из числителя и знаменателя. При W=0 total=null с причиной.
Промежуточные значения не округляются; используется Decimal.
**Инженерное допущение:** окончательное округление ROUND_HALF_UP. PDF требует
два знака, но не задаёт правило точной половины. Confidence в формулу не входит.

Decimal передаётся в JSON строками (например, `"85.38"`, `"65"`, `"55.5"`).
Frontend может форматировать отображение, но не пересчитывать авторитетный результат.

## Секции

C01–C02: «Начало и понимание запроса», исходный вес 25.
C03–C04: «Безопасность и решение», вес 40.
C05–C07: «Ведение и завершение диалога», вес 35.
C08: «Грубые нарушения», отдельно.

Вклад секции = 100 × earned_section / глобальный W.
Применимый максимум секции = 100 × applicable_weight_section / глобальный W.
Вклады до округления суммируются в общий итог. Независимо нормировать секции
и усреднять их нельзя. Это выбранный способ отображения; PDF не задаёт отдельную формулу секций.

## Регрессионные примеры

| Условия | W | earned | total |
| --- | ---: | ---: | ---: |
| Все применимые взвешенные критерии максимальны | 100 | 100 | 100.00 |
| Только C06=7, остальные максимальны | 100 | 95.5 | 95.50 |
| C02/C03=N/A, C04=15, C06=7, остальные бинарные=Да | 65 | 55.5 | 85.38 |
| То же, C08=Да | 65 | 55.5 | 85.38 + отдельный флаг |
| Нет применимых критериев с весом в изменённой конфигурации | 0 | 0 | null |

C04=17, C06=8 и N/A у C01 — ошибки валидации, не повод тихо исправить ответ.

## Валидация и evidence

Конфигурация проверяет уникальность criterion/section IDs и ступеней, ссылки на секции,
тип каждого варианта, конечные неотрицательные веса, q в [0,1], условие разрешённого N/A.
NaN/Infinity и шкала с нулевым максимумом запрещены. Исходные веса равны 100;
изменённая конфигурация может иметь другую сумму — формула нормирует её.

Набор ответов совпадает со всеми активными критериями, без дубликатов/пропусков.
Каждый ответ содержит объяснение и evidence; N/A содержит причину.
Evidence указывает на нужный snapshot и существующий диапазон сообщений.
При отсутствии действия это проверенный участок, где действие ожидалось.
Техническая корректность ссылок не заменяет смысловую проверку.

Проверки A:
`python -m pytest backend/tests/domain backend/tests/evaluation`.
Для полного изменения рубрики дополнительно выполнить генерацию контрактов
и связанные проверки из README. Scorer bootstrap отдельно передан A на смысловое ревью.
