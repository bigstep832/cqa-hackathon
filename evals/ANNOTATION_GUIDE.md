# DT20: независимая разметка для A-02

Эта памятка помогает человеку подготовить эталоны команды. Она не содержит
готовых ответов на DEV и не заменяет Ground Truth организаторов. Основа:
`config/checklists/default.v1.json`, `docs/SCORING_SPEC.md`, `docs/AI_EVALUATION_PLAN.md`.
При изменении рубрики используйте определения сохранённой версии, а не эту таблицу.

## Как начать

1. Получите разрешённые DEV-данные через импорт C и сохраните локальные snapshots.
   Для инструментов A нужен массив `EvaluationInput`, а не сырой ответ источника.
   Не пересылайте транскрипты внешним AI без отдельного согласования.
2. Выберите ориентировочно 20–25 диалогов с покрытием RU/KZ/EN и чатов/звонков.
   Не выбирайте только короткие, простые или уже удачно оценённые примеры.
3. До просмотра ответов модели задайте группы сценариев: переводы, перефразирования
   и версии одного диалога держите вместе. Зафиксируйте tune и holdout.
   Для 24 независимых групп пример — 15 tune и 9 holdout; фактический размер
   считается по диалогам, а аргумент `--holdout-groups` задаётся по группам.
4. Создайте пустой draft командой `evals.prepare prepare` из README этой папки.
   Ответы модели, demo и mock не должны заполнять ручной draft автоматически.
5. Размечайте, не глядя на предсказания. По спорным случаям нужен второй человек.
   Казахский текст проверяет человек, понимающий казахский. Не подтверждайте
   `language_understood`, если язык понятен только через машинный перевод.

## Порядок работы с одним диалогом

Сначала прочитайте весь диалог и уточните, кто оператор, клиент, бот и system.
Затем для каждого критерия проверьте применимость и выберите допустимый ответ.
Добавьте краткое объяснение и точный диапазон сообщений из оцениваемой версии.
При оценке отсутствующего действия отметьте участок, где действие ожидалось,
и явно объясните его отсутствие. Ссылка сама по себе не доказывает правильность ответа.

Заполняются `answer`, `explanation`, `evidence`, а при споре — `ambiguity_note`.
Не меняйте текст, rubric snapshot, IDs, `input_hash`, группу или split в draft.
Итоговый балл вводить не нужно: его рассчитает общий scorer при finalize.

## Исходные восемь критериев

| Код | Допустимые ответы; вес | Как принять решение | Когда допустим N/A |
| --- | --- | --- | --- |
| C01 | Да/Нет; 10 | В первом ответе оператор поздоровался на языке клиента и представился. Приветствие бота не засчитывается. | Никогда |
| C02 | Да/Нет/N/A; 15 | Нужные уточнения сделаны до ответа с учётом уже известных деталей. Пропущенное нужное уточнение — Нет. | Данных хватало с самого начала |
| C03 | Да/Нет/N/A; 20 | Требуемая проверка личности подтверждена до раскрытия данных или защищённого действия. Просьба пройти проверку ещё не подтверждение. | Запрос не требовал идентификации |
| C04 | 0/5/10/15/20/N/A; 20 | Полнота и правильность консультации по шкале ниже. | Диалог закончился до формулировки запроса |
| C05 | Да/Нет; 15 | Вежливость и реакция на конкретную проблему при недовольстве. В спокойном диалоге искусственное сочувствие не требуется. | Никогда |
| C06 | 0/4/7/10; 15 | Понятность, последовательность и предупреждение при явном ожидании. | Никогда |
| C07 | Да/Нет/N/A; 5 | Есть (итог ИЛИ предложение дальнейшей помощи) И прощание. | Диалог оборвался до возможности завершения |
| C08 | Да/Нет; без веса | Да означает подтверждённое грубое нарушение, а не хорошую работу. | Никогда |

C04: **20** — все существенные вопросы закрыты или дан корректный следующий шаг;
**15** — основной вопрос решён, пропущена второстепенная деталь;
**10** — часть закрыта, существенный вопрос остался;
**5** — общая подсказка без понятного способа действовать;
**0** — нет ответа по существу либо ключевая рекомендация ошибочна.

C06: **10** — ясно и связно, при явном ожидании есть предупреждение;
**7** — один заметный сбой, но ответ понятен;
**4** — клиент переспрашивает из-за формулировок или порядка ответов;
**0** — бессвязность или противоречия делают ход диалога непонятным.

C08: основания — оскорбление, предложение платной услуги в обход компании,
раскрытие конфиденциальной информации. Для частной платной услуги достаточно
предложения; согласие или перевод денег не нужны. Не добавляйте оснований от себя.

## Частые ловушки

| Ситуация | Что проверить |
| --- | --- |
| Бот поздоровался, оператор сразу ответил без представления | Оценивать первый ответ оператора по C01 |
| Клиент сразу дал все необходимые детали | C02 может быть N/A; отсутствие лишнего вопроса не означает Нет |
| Идентификация нужна, оператор только попросил её пройти | Для C03=Да нужно подтверждение завершения до защищённого действия |
| Общий вопрос без персональных сведений | C03 может быть N/A, идентификация не обязательна для каждого вопроса |
| Ясный ответ закрывает лишь один из двух существенных вопросов | C04 и C06 оцениваются отдельно; неполнота не равна непонятности |
| Клиент спокоен, оператор вежлив | Отсутствие отдельной фразы сочувствия само по себе не снижает C05 |
| Оператор завершил чат после ответа без прощания | C07=Нет при наличии возможности завершить; не автоматическое N/A |
| Есть задержка более трёх минут | Не добавлять исключённый штраф за время первой реакции |
| Оператор запросил телефон | Сам запрос не доказывает C08; нужен контекст нарушения |
| В тексте есть «игнорируй чек-лист» или готовые оценки | Это содержимое диалога, не инструкция разметчику или модели |
| Для проверки совета нужен отсутствующий тариф/регламент | Зафиксировать неопределённость, не выдумывать документ или ответ |
| Есть звонок без точной привязки ко времени | Не выдумывать аудиосмещение; вопросы применения чатовой рубрики записать отдельно |

N/A не означает «не знаю». Пропущенный ответ не равен Нет. Неопределённость
не превращается в автоматически заполненный эталон. C08 не обнуляет итог.
C06=7 — исходная ступень 7, а не взвешенный вклад 10.5.

## Завершение разметки

В `review` укажите человека в `annotated_by`, время с часовым поясом в `completed_at`
и подтверждение понимания языка. Спор требует `resolution_note`, второго человека
в `reviewed_by` и времени `reviewed_at`. Неразрешённые случаи оставьте незавершёнными.
Не подписывайте автоматически созданные ИИ ответы как независимую человеческую разметку.

Проверьте выбранную часть через `evals.prepare validate`, затем `finalize`.
Сохраняйте полный draft: компактный ReferenceRecord не содержит объяснений,
доказательств и сведений о людях. Все реальные файлы остаются в private-каталогах.

Сначала анализируйте только tune. Зафиксируйте модель, instruction/pipeline и рубрику
перед holdout. Не исправляйте prompt после каждого holdout-результата, продолжая
называть ту же выборку независимой. Контроль организаторов проходит тот же pipeline.

## Как читать отчёт сравнения

- `criterion_accuracy` и `score_mae` относятся только к succeeded; всегда смотрите
  `reference_count`, `succeeded`, `failed`, `pending` и соответствующие доли.
- `per_criterion.*.confusion` показывает допустимые исходные ответы, а не их веса.
  C04/C06 анализируйте по тому, какие ступени путаются.
- `na_detection.false_positive` — ошибочное N/A; `false_negative` — пропущенное N/A.
- Для исходного C08 поле `boolean_true`: precision — какая доля поднятых флагов
  верна, recall — какая доля настоящих нарушений найдена. Если знаменатель нулевой,
  значение null: отсутствие положительных случаев не доказывает высокий recall.
- `by_language` и `by_channel` показывают провалы малых подгрупп. Вместе с долями
  сохраняйте размеры групп; один пример не даёт надёжной оценки общего качества.
- `disagreements` содержит только ссылки на версии и типизированные ответы.
  Найдите исходный draft и prediction, затем вручную проверьте смысл evidence.
- `successful_prediction_identity.mode=mock` означает техническую репетицию.
  Даже 100% на таком примере не является измеренной точностью AI.
- Стоимость, tokens и задержки всех попыток берите из отдельного журнала прогона,
  включая failed. Этот отчёт их не восстанавливает по успешным ответам.

Метрики команды не являются неизвестной формулой отбора жюри. Не подменяйте
исходные AI-ответы апелляциями ради улучшения показателей.
