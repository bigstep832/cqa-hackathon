# B-04: проверка истории

Все данные этих сценариев синтетические. Внешние AI-запросы не выполняются.

## Команды из frontend

- `npm.cmd run typecheck`
- `npm.cmd run lint`
- `npm.cmd run test`
- `npm.cmd run build`
- `npm.cmd run generate:api:check`
- PowerShell: `$env:CQA_BROWSER_CHANNEL='msedge'`
- `npm.cmd run test:e2e -- --workers=2 --output=test-results/regressions`
- `npm.cmd run test:e2e:history`

На других ОС используйте `npm`. Зависимости должны быть уже установлены.
Обычный e2e-набор требует рабочего FastAPI на 8000. Его тесты demo и appeals-real
работают с настоящим API, остальные сценарии используют перехват транспорта.

## Изолированный FastAPI + SQLite

`playwright.history.config.ts` поднимает собственные процессы на 8001 и 5174,
не переиспользует и не останавливает существующий backend. Порты должны быть свободны.
Python по умолчанию берётся из корневой `.venv`; другой установленный интерпретатор
можно задать через `CQA_TEST_PYTHON`.

`tests/support/history_backend.py` создаёт новый SQLite и нулевой бюджетный local-план
в игнорируемом `frontend/test-results/history-db-*/`. Backend-файлы не меняются.
В отдельном процессе заменяются только два транспорта:

- источник импорта возвращает публичную синтетическую fixture, затем изменённый текст v2;
- транспорт оценщика возвращает заранее заданные синтетические ответы. Сетевой сокет
  провайдера не открывается, реальные ключи не используются.

API, разрешения выполнения, очередь, адаптер, валидация, scorer, хранение snapshots,
история и SQLite выполняются настоящим backend. В запросе используется `mode=live`
для проверки этого workflow; это **не проверка реального AI-провайдера**.
Встроенный mock для вручную импортированного диалога не разрешается и не обходится.

C разрешает Origin для POST только на 5173/8000. Изолированный тестовый Vite proxy
на 5174 передаёт Origin 5173 на внутреннем переходе к FastAPI. Рабочая Vite-конфигурация
и правила backend не меняются. Этот стенд не проверяет политику Origin развёртывания.

## Что проверяет настоящий сценарий

Импорт v1 через HTTP POST datasets/import → запуск оценки из UI → HTTP-импорт v2 →
полная перезагрузка страницы → выбор диалога из списка → история → оценка v1 →
evidence исходной реплики v1. ID оценки не вводится в форму, адрес или storage.

Проверяются ровно один POST оценки, серверные 85.38, обе версии в истории,
неизменность v1, исторический ChecklistVersion, отсутствие текста v2 в результате,
фокус evidence и ширина 390 px. Скриншоты сохраняются в
`test-results/history-integration/`. Импорт через пользовательскую JSON-форму
проверяется отдельными регрессионными тестами; в этом сценарии импорт — через HTTP.

## Границы и совместная проверка с C

Обработка 404/422/500/сети, retry, пагинация и несколько статусов покрыты
Vitest и Playwright с заглушками API. Настоящая проверка истории использует два
импорта и одну успешную оценку; большие страницы и аварии SQLite в неё не входят.
С C остаётся проверить историю в общем окружении на его запущенной версии backend.
После интеграции C ранее запущенный Python-процесс надо перезапустить, чтобы он
обслуживал новые маршруты. Ни mock fallback, ни клиентский пересчёт баллов не добавлены.
